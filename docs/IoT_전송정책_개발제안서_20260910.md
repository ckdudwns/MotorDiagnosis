# IoT 담당자 전달용 — 5분 묶음 전송·이상 징후 우선 전송 개발 제안서

작성일: 2026-09-10  
프로젝트: Bind Edge AI Motor Diagnosis  
대상: ESP32-S3 + ADXL345(SPI) + INMP441(I2S), `DEV-01-MOT-02`  
작업 브랜치: `feat/adaptive-https-transmission`  
기준 코드: `348f1ce` 이후 전송 정책 변경. 현재 담당자 보드의 최신 FIFO/LittleFS 개선본과 병합이 필요합니다.

## 1. 제안 목적

센서 측정은 연속으로 유지하되, 평상시 HTTPS 요청 횟수를 줄이고 이상 징후가 발생하면 빠르게 서버에 데이터를 전달합니다.

- 평상시: 원시 진동을 계속 보관하고 **5분마다 묶음 업로드**.
- 이상 징후: 보드의 가벼운 규칙으로 먼저 감지하여 **즉시 우선 업로드**.
- 모델: RF66은 서버에서 실행. 보드에 RF66이나 Python 런타임을 올리지 않음.
- 프로토콜: 기존 HTTPS·Bearer 인증 유지. MQTT 추가 없음.
- 보드의 감지는 **전송 시작 조건**이며 RF66 판정이나 모터 고장 확정이 아님.

## 2. 바뀌지 않는 입력 규격

| 항목 | 규격 |
|---|---|
| 진동 입력 | ADXL345, 800Hz, XYZ 축별 512샘플, 명목 640ms |
| 서버 원시 입력 | `adxl345-800hz-xyz-counts-v1` |
| 전송 표현 | XYZ interleaved signed int16 little-endian → base64 |
| 단위 | `count`, `gPerCount=0.0039` |
| 원시 데이터 크기 | 유효 구간당 3,072바이트, base64 4,096문자 + 메타데이터 |
| 서버 모델 | 원시 구간 → 66개 특징 → RF66 |
| 연속 확인 | 서버의 기존 연속 3구간 정책 유지, 시작 간격 630~670ms |
| 음향 | 기존 연속 I2S 수집 유지. 이번 1차 감지는 진동 기반 |

5분은 **전송 대기 주기**입니다. 센서 샘플링이나 구간 생성 주기를 5분으로 변경하지 않습니다. 음향은 기존 요약값을 보관하며, 모든 원시 음향 파형을 5분간 저장하는 기능은 이번 범위에 포함하지 않습니다.

## 3. 보드의 가벼운 1차 감지

구간별 평균 제거 후 XYZ RMS의 합성값 `sqrt(rmsX²+rmsY²+rmsZ²)`과 축별 AC peak 중 최댓값을 사용합니다. 기존 21개 특징 계산 결과를 재사용합니다.

| 항목 | 조건 | 동작 |
|---|---|---|
| 진동 감소 | 정상 RMS 하한 미만이 최근 3구간 중 2개 | 우선 전송 시작 |
| 진동 증가 | 정상 RMS 상한 초과가 최근 3구간 중 2개 | 우선 전송 시작 |
| 심한 변화 | 심각 RMS 하한 미만 / 상한 초과 / AC peak 상한 초과 중 하나 | 1구간으로 우선 전송 |
| 측정 불가 | FIFO overrun, 샘플 누락, 센서 장애, 포화, 상수 축, 비유한 값 | 장치·측정 오류로 구분하여 우선 전송 |
| 기준 미설정 | 정상 기준 미설정 또는 설정값 검증 실패 | 5분 대기를 사용하지 않고 짧은 주기 전송 유지 |

- 조건들은 AND가 아니라 OR입니다. 민감하게 감지하여 놓침을 줄이는 용도입니다.
- 부팅·구간 번호 불연속·시각 불연속·측정 불량 시 2-of-3 누적 상태를 끊습니다.
- 정상 범위가 연속 **30초** 유지되면 정기 모드로 복귀합니다. 30초는 변경 가능한 초기 운영 설정이며, 검증된 최적값을 의미하지 않습니다.
- 구간 시각을 기준으로 복귀 시간을 계산하며, 중간 누락이나 품질 불량을 정상 유지 시간에 합산하지 않습니다.
- 진동 급감은 정지 또는 상태 변화의 징후입니다. 물 흐름 중단·펌프 고장을 단독 확정하지 않습니다.

### 정상 기준값 설정

`firmware/esp32_edge_node/include/adaptive_transmission.local.h`에 아래 이름으로 실제 모터에서 정한 값을 입력합니다. 이 로컬 파일은 Git에서 제외됩니다.

```cpp
#define ADAPTIVE_BASELINE_ID "대상모터-운전조건-기준버전"
#define ADAPTIVE_RMS_LOW_G       /* 정상 합성 AC RMS 하한 */
#define ADAPTIVE_RMS_HIGH_G      /* 정상 합성 AC RMS 상한 */
#define ADAPTIVE_SEVERE_LOW_G    /* 심각 RMS 하한 */
#define ADAPTIVE_SEVERE_HIGH_G   /* 심각 RMS 상한 */
#define ADAPTIVE_SEVERE_PEAK_G   /* 축별 AC peak 최댓값의 심각 상한 */
#define ADAPTIVE_RECOVERY_MS 30000
```

위 코드는 변수 설명용 템플릿입니다. 주석 부분을 실제 숫자로 채우기 전에는 사용하지 않습니다. 순서는 `0 ≤ severeLow < low < high < severeHigh`이고 peak 상한은 양수입니다. 단위는 모두 `g`이며 raw count·mm/s·dB를 그대로 넣으면 안 됩니다.

실제 대상 모터의 정상 부하·설치 상태에서 정상 범위와 정지/기동 구간을 확인해 설정합니다. 과거 PC 측정 결과로 펌프 기준을 대신 정하지 않습니다. 기준을 자동 학습하거나 이상 상태에 맞춰 자동 갱신하지 않습니다. 운전 조건이 달라지면 별도 기준 버전으로 관리합니다.

## 4. 전송·보관 동작

### 정상 모드

1. 모든 원시 진동 구간을 생성합니다.
2. 별도 저장 태스크가 구간별 파일을 LittleFS에 기록합니다.
3. 300,000ms마다 그 시점까지 쌓인 구간을 업로드 대상으로 고정합니다.
4. **한 요청에 최대 4구간**씩 나눠 전송합니다. 업로드 중에도 수집은 계속합니다.
5. HTTP 200/202와 ACK의 deviceId·bootId·windowIndex 목록을 확인한 후 해당 원본을 제거합니다.

### 우선 모드

- 1차 감지 시 5분 대기를 해제합니다.
- 아직 보관 중인 직전 최대 3구간과 감지 구간·이후 구간을 우선 대상으로 지정합니다. 이미 ACK되어 서버에 저장된 직전 구간은 다시 보낼 필요가 없습니다.
- 과거 정기 묶음보다 우선 구간을 먼저 보냅니다. 이미 진행 중인 HTTP 요청을 강제로 중단하지는 않습니다.
- 우선 전송은 네트워크 태스크가 처리합니다. 센서 태스크에서 HTTPS를 실행하지 않습니다.
- 감지 지속 중에는 짧은 묶음 전송을 이어갑니다. 네트워크 상태에 관계없이 일정 초 이내 전달된다는 보장은 아닙니다.

### 통신·저장 장애

- HTTP 오류, 타임아웃, ACK 유실·불일치에서는 파일을 제거하지 않습니다.
- 재전송 시 구간 식별자·측정 시각·샘플을 유지합니다. 서버는 동일 구간 중복을 ACK하고 다른 내용의 동일 식별자는 거부합니다.
- 재부팅 후 남아 있는 파일을 복원합니다. CRC 검증 실패나 불완전 저장은 자동 포맷하거나 정상 데이터로 처리하지 않습니다.
- 오래된 부팅에서 UTC 기준을 확보하지 못한 파일은 보존하고 전송 대상에서 제외합니다. 새 부팅 시각을 끼워 넣지 않습니다. 시작 로그에서 `Preserved unresolved UTC`를 확인해야 합니다.
- 저장 슬롯 600개 이상 또는 저장 문제가 감지되면 5분 전이라도 정기 업로드를 시작합니다.
- 슬롯이 모두 차면 미확인 파일을 덮어쓰지 않습니다. 새 구간이 RAM 대기열에서도 수용되지 않으면 누락 카운터와 구간 번호의 공백으로 드러납니다. 누락 카운터는 부팅별 값이며, 전원 차단 전 아직 영구 기록되지 못한 구간의 완전 보존은 보장하지 않습니다.

## 5. 서버 API 합의안과 구현

```text
POST https://motordiagnosis-api.duckdns.org/api/devices/DEV-01-MOT-02/raw-vibration-windows
Authorization: Bearer <기존 해당 장치 ingest 토큰>
Content-Type: application/json
```

기존 `windows` 내부 형식은 그대로 유지하고, 요청 최상위에 선택 항목 `transmission`을 추가했습니다.

```json
{
  "windows": ["기존 원시 구간 객체, 최대 4개 — 설명용 자리표시자"],
  "transmission": {
    "policyId": "edge-trigger-batch-v1",
    "mode": "priority",
    "reason": "rms_high",
    "baselineId": "pump-normal-v1",
    "droppedWindows": 0
  }
}
```

위 예시의 windows 문자열은 설명용입니다. 실제 요청에는 기존 구간 JSON 객체를 넣습니다.

| 필드 | 값 |
|---|---|
| mode | `periodic`, `priority`, `replay` |
| reason | `none`, `rms_low`, `rms_high`, `severe`, `quality`, `baseline_missing`, `storage_pressure`, `recovery_hold` |
| baselineId | 실제 정상 기준 버전. 미설정은 `unconfigured` |
| droppedWindows | 해당 부팅의 누적 수집/처리 대기열 누락 수 |

서버 적용 내용:

- 구형 요청(`windows`만 전송)은 기존 계약대로 처리합니다.
- 신규 구간은 HTTP 202, 동일 원본 중복은 HTTP 200으로 ACK합니다. ACK는 저장 확인이며 RF66 판정 성공이라는 뜻은 아닙니다.
- 선택적 메타데이터를 사용하는 `periodic/replay` 요청은 우선 전송보다 늦게 온 과거 공백 구간도 수용합니다. 기존 매핑·측정 시각/uptime·정체성·데이터 충돌 검사는 유지합니다.
- 우선 요청의 분석 작업을 과거 묶음보다 먼저 처리합니다.
- 모든 유효 구간은 RF66 분석 대상으로 유지합니다. 실시간/이력 연속 확인 상태를 분리합니다.
- 정기·재전송 데이터와 오래된 우선 구간은 분석 이력으로 남기되 현재 이벤트를 열거나 닫지 않습니다. 보드가 놓친 이상은 정기 분석의 후보 이력에서 발견될 수 있지만 즉시 알림과 동일하지 않습니다.
- 서버 수신 시각, 전송 모드·사유·기준 버전은 분석 결과의 `transmission` 필드에 남깁니다.
- 운영 점검에서 정기 입력의 예상 최대 측정 나이는 **360초(5분+전송 여유 1분)**로 구분합니다. 우선/구형 입력과 실제 이벤트의 관측 신선도는 기존 30초 기준을 유지합니다. 정기 원시 묶음의 분석 대기 시간은 수집 시각 대신 서버 접수 시각으로 계산합니다.
- `events` 모드와 RF66 임계값, 외부 알림 활성화 조건은 이번 변경으로 바꾸지 않습니다.

현재 펌웨어는 재부팅 복원분도 정기 묶음(`periodic`)으로 보낼 수 있습니다. `replay`는 같은 과거 수용 의미를 갖는 서버 지원 값입니다. 메타데이터만 바꿔 중복 요청해도 이미 저장된 원본을 실시간 판정으로 승격시키지 않습니다.

서버의 원시 구간 수용 시간 범위는 기존 48시간을 유지합니다. 그보다 오래된 미전송 파일은 자동 폐기하거나 시각을 바꿔 보내지 않으며, 담당자가 별도 회수·보존 절차로 처리해야 합니다. 영구적인 400/409 거부나 손상 파일이 있으면 로그 확인과 수동 복구가 필요합니다.

## 6. N8 저장 공간과 빌드 프로필 — 적용 전 필수 확인

5분에는 명목상 약 469개 구간이 생성됩니다. XYZ int16 원시 데이터만 약 **1.44MB(십진 단위)**이며, 메타데이터·파일시스템 여유 공간은 별도로 필요합니다. 기존 N8 기본 파일시스템은 1.5MiB이고 기존 telemetry 저장소도 사용하므로 충분하지 않습니다.

별도 프로필 `esp32-s3-devkitc-1-n8-adaptive`를 추가했습니다.

- Flash 8MB, **PSRAM 의존 없음**.
- 앱 영역 약 3.19MiB, 파일시스템 약 4.69MiB.
- 원시 저장은 최대 768슬롯. 기존 telemetry 저장소와 파일시스템 공간을 공유합니다.
- 두 번째 OTA 앱 슬롯을 없앤 구성입니다. **기존 듀얼 슬롯 OTA 업데이트 방식을 그대로 사용할 수 없습니다.**
- 기본 N8 프로필과 기본 빌드 대상은 바꾸지 않았습니다.

**파티션 위치가 바뀌므로 기존 장치에 바로 덮어 올리면 안 됩니다.** 먼저 전송 대기 데이터와 기존 LittleFS 파일을 안전하게 백업하고, 복구 가능한지 확인한 뒤 담당자가 마이그레이션해야 합니다. 이번 작업에서는 보드 업로드·포맷·플래시 삭제를 수행하지 않았습니다.

OTA 유지가 필수라면 현재 프로필을 채택하지 말고 외부 저장 공간 등 별도 보관 방식을 협의해야 합니다.

| 정상 10분 이상 | 800Hz/512샘플 구간 생성 지속, 약 5분마다 원시 묶음 업로드 시작 |
| 1구간 작은 변화 | 2-of-3 미충족으로 불필요한 우선 전송 억제 |
| 최근 3구간 중 2구간 기준 이탈 | reason 및 우선 전송 시작, 서버 원시/분석 저장 |
| 심한 변화·센서 분리 | 1구간 조건으로 전송, 오류를 정상 판정으로 만들지 않음 |
| 정상 복귀 | 누락 없이 유효 정상 구간 30초 유지 후 정기 모드 |
| 정기 업로드 중 이상 | 다음 전송 기회에 우선 구간을 먼저 전달, 과거 원본은 보존 |
| Wi-Fi 단절·HTTP/ACK 유실 | 파일 유지, 복구 후 중복 ACK, 잘못된 ACK에는 제거하지 않음 |
| 재부팅·저장 도중 전원 차단 | 기존 파일 보존/복원 또는 명시적 CRC·미완료 오류, 임의 포맷 없음 |
| 저장 공간 부족 | 조기 업로드, 원본 덮어쓰기 없음, 누락·대기 상태 확인 |
| 과거 묶음 뒤늦게 도착 | 서버 분석 이력 저장, 현재 RF66 사건 유지·해제에 영향 없음 |

필수 로그: bootId, windowIndex 범위, 실제 sampleCount/quality, 전송 mode/reason, HTTP 코드, ACK 구간 목록, pending/drops, 센서 FIFO 최대 읽기 간격, 최소 free heap/largest block, 태스크 stack high-water mark.

4구간은 명목상 2.56초의 원시 측정량입니다. 연속 우선 전송 시 평균 처리량이 이 생성량을 따라가는지 확인해야 합니다. 별도 태스크와 묶음 전송만으로 FIFO overrun이 사라졌다고 판단하지 않습니다. 특히 내부 Flash 기록 중 캐시 지연과 기존 capture health 큐의 대기를 실측해 주세요.

장치 health·통신 품질 보고는 정기 원시 업로드와 별도로 유지합니다. 기존 health 전이와 telemetry 순서 보장을 위해 요약 전송이 5분 전 실행되는 예외는 허용합니다. 전체 전원/네트워크 장애는 보드의 즉시 전송 대신 서버의 수신 시간 초과로 감지합니다.
