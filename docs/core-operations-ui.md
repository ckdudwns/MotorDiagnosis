# 핵심 운영 화면 — 장치 운영 연결

기존 UI-01~05(이벤트 상세·검수·메모·신호 차트·CSV/XLSX 내보내기),
기준정보 관리와 AI 결과 검토 화면을 유지하면서 UI-06의 장치 운영을 연결한다.
이번 변경은 기존 API를 사용하는 화면과 회귀 검사다. 백엔드 계약, 펌웨어,
기획·API 명세 파일을 변경하지 않는다.

## 화면과 사용 순서

1. 로그인 후 사이트와 설비를 선택하고 **장치 운영**을 연다.
2. 선택 설비에 매핑된 장치 중 확인할 장치를 고른다. 활성 장치를 우선 선택하며,
   비활성 장치도 상태·이력 조회를 위해 표시한다. 다른 설비의 장치를 섞지 않는다.
3. 연결 상태, 최근 수신, RSSI, 재부팅, 버퍼 사용률, 센서 상태를 확인한다.
   센서 고장과 세부 필드는 펼침 원문에서 확인한다.
4. 품질 조회 기간(1/6/24시간, 7/30일)과 집계 간격(1/5분, 1시간, 1일)을 정한다.
   **상태·품질 조회**로 갱신한다. 1,000개 구간을 초과하면 기존 표를 비우고
   집계 간격을 늘리도록 안내한다. 구간별 표는 12개씩 모두 탐색할 수 있다.
5. 설정 상태에서 서버 최신 요청과 장치의 마지막 적용 성공 보고를 비교한다.
   변경하려면 허용된 두 값과 사유를 입력하고 **설정 요청 발행**으로 대상을 확인한다.
6. **서버 설정 다시 확인**과 **이력 새로고침**으로 장치 결과를 확인한다.
   설정 이력은 서버가 보관하는 현재 매핑의 최근 100개 요청·최종 결과이며,
   12개씩 페이지를 이동한다. 모든 상태 전환을 무제한 보관하는 감사 로그는 아니다.

장치 운영의 품질 기간은 텔레메트리·이벤트의 조회 기간과 독립적이다. 이 화면에서는
상단 텔레메트리 기간 선택기를 숨기고 품질 기간 선택기를 사용한다. 서버에는 절대 UTC
시각을 전달하며, 조회 범위·완료 시각은 브라우저의 현지 시각으로 표시한다.

## 표시와 권한

| 항목 | 처리 |
| --- | --- |
| 장치 목록·health·품질·설정·이력 조회 | 기존 사용자 세션의 `device:read` 및 서버 사이트 접근 검사 |
| 설정 발행 | `device:read`와 `parameter:write`, 활성 매핑·등록 인증서·지원 ID 계약 필요 |
| 읽기 전용·비활성·지원하지 않는 ID | 조회는 유지하고 설정 편집·발행은 비활성화 |
| 관측 창 없음 | `hasData: false`를 **관측 없음**으로 표시; 합계 0만으로 정상 판정하지 않음 |
| 관측된 0 | 전송 시도 0·버퍼 깊이 0·ACK 지연 0ms는 유효한 값으로 유지 |
| ACK 없는 관측 창 | 지연 `null`을 미수신으로 표시; 0ms로 대체하지 않음 |
| 상태·품질·설정·이력 조회 실패 | 실패한 영역의 이전 결과를 비우고 오류 표시; 다른 영역의 결과는 유지 |
| 설정 조회 실패 | 다시 조회하기 전까지 발행 비활성화 |

품질 수치는 기존 HTTP 장치 관측 API의 값이다. ACK 평균은 서버의 가중 평균을 그대로
표시하고, 버퍼 평균은 시간 가중 평균이 아닌 표본 평균임을 명시한다. 긴 관측 창은
종료 시각의 구간에 통째로 귀속되므로 경계 초과 창, 최초 시작·마지막 종료·지속시간 합을
함께 확인한다. MQTT PUBACK 지연이나 네트워크만의 RTT로 해석하지 않는다.

## 설정 요청과 실제 적용의 구분

- 편집 항목은 `measurementIntervalMs`(3,000–60,000 정수)와
  `replayBatchSize`(1–4 정수)뿐이다. 변경 사유는 공백 제거 후 1–1,000자다.
- 측정 후 대기 시간은 정확한 측정 시작 간격을 보장하지 않는다. 모터 RPM 제어,
  센서 설정, 인증정보, 네트워크, OTA, 버퍼 초기화는 제공하지 않는다.
- 최초 화면의 기본값은 편집용 제안이지 장치의 실제 적용값이 아니다.
- PUT 성공은 서버의 `pending` 요청 저장이다. 장치의 별도 결과가 `applied`로
  보고되기 전에는 적용 완료로 표시하지 않는다. `failed`/`rejected` 상태에서도
  마지막 성공 보고는 별도로 유지한다. 성공 보고 역시 현재 실시간 상태의 보장은 아니다.
- 화면은 조회한 `expectedVersion`을 전송한다. 충돌 시 초안을 보존하고 서버 설정을
  명시적으로 다시 확인하게 한다. 새 버전을 확인한 후에만 다음 발행을 허용한다.
- 응답이 유실되거나 형식이 맞지 않으면 자동 재발행하지 않고 잠근다. GET에서 요청한
  다음 버전·두 설정·사유가 일치하면 이미 존재하는 요청으로 처리한다. 다른 버전이면
  초안을 보존해 비교하게 한다. 같은 pending/applied 설정의 중복 요청도 막는다.
- PUT 성공 직후 초안을 확정하고 이력을 갱신한다. 후속 조회 실패가 저장 성공을
  되돌리거나 같은 PUT을 다시 보내게 하지 않는다.

발행 중에는 대상 전환과 중복 제출을 막는다. 조회 중에는 사용자·사이트·설비·장치와
요청 번호를 확인해 이전 응답이 새 결과를 덮어쓰지 못하게 한다. 상태·품질 조회는
작성 중인 설정을 지우지 않는다. 장치 운영에서는 기존 5초 텔레메트리 갱신을 수행하지
않으며, 화면 이동 후 돌아와도 작성 중인 초안을 유지한다. 브라우저 새로고침·종료 후
초안을 보관하거나 미확인 요청을 자동 복구하는 로컬 저장 기능은 제공하지 않는다.

## API와 운영 전제

- `GET /api/sites/{siteId}/devices`
- `GET /api/devices/{deviceId}/health`
- `GET /api/devices/{deviceId}/communication-quality?from=...&to=...&bucketSeconds=...`
- `GET`, `PUT /api/devices/{deviceId}/configuration`
- `GET /api/devices/{deviceId}/configuration/history`

브라우저는 기존 사용자 세션만 사용한다. 장치 전용 토큰을 화면에서 입력·조회·보관하지
않는다. 실제 장치의 품질/설정 채널은 기존 배포 절차로 별도 활성화해야 한다.
미활성화된 장치는 관측 없음 또는 적용 보고 대기 상태일 수 있으며, 화면에서 임의로
정상/적용 성공을 생성하지 않는다.

- `tests/test_core_operations.py`: 실제 HTTP 6개 검사. 장치 범위·초기 설정,
  품질 없음/0/실패/ACK, pending→applied→failed, 버전 충돌, 사용자와 장치 채널의
  권한 분리를 독립 임시 DB로 확인한다.
- 전체 백엔드: 348개 실행, 346개 통과·선택 의존성 관련 2개 건너뜀.
- 로컬 시험 브라우저에서 로그인→설비 선택→장치 운영, 품질 요약과 적용 성공 보고의
  실제 표시를 확인했다. 발행 확인창에서는 브라우저 제어 도구가 시간 초과되어
  이후 클릭 흐름의 시각 검증은 완료하지 못했다. 해당 발행 로직은 위 JS/HTTP 검사로
  검증했으며, 운영 브라우저의 최종 수동 확인이 필요하다.
- 실제 장치 설정 발행, 서비스 배포, 보드 업로드·전원 차단·실환경 TLS 시험은 미실행이다.
