# 제한된 원격 장치 설정

## 범위

ESP32가 HTTPS로 자신의 설정을 조회하고, 버전과 설정을 NVS에 함께 저장·읽기 검증한 후 메인 루프에 적용한다. 장치는 적용 결과를 별도로 보고한다. 서버에 저장됐다는 이유만으로 적용 성공으로 표시하지 않는다.

| 설정 | 허용 범위 | 기본값 | 실제 실행 효과 |
| --- | --- | --- | --- |
| `measurementIntervalMs` | 정수 3000–60000 | 3000 | 각 측정/전송 사이클 뒤 대기 시간. 정확한 측정 시작 간격이나 전송 주기 보장은 아니며 취득·HTTP·재전송 처리 시간도 더해진다. |
| `replayBatchSize` | 정수 1–4 | 4 | 한 메인 루프에서 처리할 과거 버퍼 기록의 최대 수. 신선한 측정으로 복귀하기 전의 상한이다. |

최소 대기 시간을 기존 3초보다 줄이지 않고, 재전송 상한도 기존 4건보다 늘리지 않는다. 기존 링의 물리적 크기·보존 정책·ACK·sequence·레코드 형식은 바꾸지 않는다. 버퍼를 비우거나 저장소를 초기화하는 원격 명령은 없다.

Wi-Fi/인증정보/서버 주소/TLS 신뢰 설정, 센서 핀·샘플링률·단위 보정, 임의 코드·명령 실행, 모터 속도 제어, 펌웨어 OTA는 지원하지 않는다. 이 변경은 IoT와 백엔드 API 범위이며 별도 원격 설정 편집 화면은 포함하지 않는다.

전역 `/api/parameters`의 `TELEMETRY_INTERVAL_SEC`와 버퍼 관련 값은 계속 읽기 전용이다. 이 값들을 장치의 실제 적용 설정으로 간주하지 말고 아래 장치별 API를 사용한다.

## 발행·적용 상태

관리자 발행 → `pending` → 장치 조회 → NVS 저장/읽기 검증 → 메인 루프 적용 → 결과 보고 → `applied`

- 서버 `desired`는 최신 요청이며, `lastApplied`는 마지막으로 장치가 적용했다고 보고한 설정이다. 현재의 연결 상태나 즉시 적용 여부를 보증하는 실시간 값이 아니다.
- `failed`/`rejected`는 장치의 오류 보고다. 장치의 적용 성공 보고가 오기 전에는 이전 `lastApplied`를 유지한다. 일시적 저장 오류에서 회복하면 같은 버전을 다시 적용·보고할 수 있다.
- 최신 요청만 전달한다. 여러 요청 사이의 중간 버전은 적용되지 않을 수 있다. 과거 설정으로 되돌릴 때도 기존 값을 **더 높은 새 버전**으로 발행한다.
- 발행은 `expectedVersion`으로 동시 편집을 검사한다. 성공 응답을 잃고 재시도하면 409가 발생할 수 있으므로 먼저 현재 버전을 다시 조회한다. 같은 기대 버전으로 중복 명령을 만들지 않는다.
- 결과는 장치·버전·`commandId`·요청 설정과 일치해야 한다. 새 버전 발행 후 도착한 이전 결과는 409로 거부하며 최신 상태를 덮어쓰지 않는다.
- 동일 적용 성공 결과를 다시 보내도 감사 이력과 저장 상태가 중복 갱신되지 않는다. 이미 `applied`인 버전의 늦은 실패 보고는 거부한다.
- 장치별 최근 100개 요청/최종 결과를 조회할 수 있다. 요청과 상태가 바뀌는 결과는 기존 감사 로그에도 기록한다. 발신 토큰은 상태 DB·감사에 넣지 않는다.

## 인증과 운영 준비

원격 설정 채널은 **펌웨어 기본 비활성**이다. 예제에 작동하는 공통 데모 토큰을 넣지 않았다.

1. 백엔드를 먼저 배포한다. 일반 상태 저장소(`STATE_DB_PATH`)가 영속 경로를 사용해야 요청·결과·감사·버전이 재시작 후 유지된다. 운영 실행 진입점의 기본값은 `output/runtime.sqlite3`이며, `create_server()` 테스트의 메모리 모드와 구분한다.
2. 서버의 `DEVICE_CONFIG_TOKENS_JSON`에 `장치 ID → 그 장치만의 토큰` JSON 객체를 비밀 저장소/환경변수로 주입한다. 원격 설정의 장치·사이트·설비 ID는 모두 `[A-Z0-9][A-Z0-9_.-]{0,62}`를 따른다. 대문자 영숫자로 시작하고 영숫자·`.`·`_`·`-`로 최대 63 ASCII 바이트다. 토큰은 충분한 엔트로피로 생성한 32–128자의 영숫자·`_`·`-` 문자열을 사용한다. 길이 검사는 엔트로피를 보장하지 않는다.
3. 같은 토큰을 여러 장치에 공유할 수 없다. 중복 JSON 키나 잘못된 토큰 구성이면 채널 인증을 503으로 거부한다. 일반 ingest/health 토큰과 관리자 세션은 장치 설정 조회·결과 보고에 사용할 수 없다.
4. Git에서 제외된 장치의 `secrets.h`에 `DEVICE_CONFIG_TOKEN_VALUE`와 `DEVICE_CONFIG_URL_VALUE`를 설정한다. 주소는 예를 들어 `https://backend.example.com/api/devices/DEV-01-MOT-02/configuration`이며, 끝의 `/`, 쿼리 문자열, 다른 장치 ID를 넣지 않는다. 실제 사이트·설비·장치 ID와 매핑도 일치해야 한다.
5. 기존 백엔드 CA 인증서·시계 동기화·HTTPS 검증을 사용한다. 리디렉션을 따라가지 않고 원격 응답에서 다른 주소를 받아 접속하지 않는다. HTTP 예외는 기존 명시적 로컬 개발 옵션으로만 허용한다. 외부 운영망에는 HTTPS를 제공하고 기존 운영 사용자 계정·접근 정책도 점검한다.
6. 장치별 신규 펌웨어를 배포한 뒤 요청/보고 상태를 확인한다. 이 개발 작업에서는 실제 토큰 주입·배포·보드 업로드를 하지 않았다.

기존 일반 상태 저장소를 소유하는 **단일 백엔드 프로세스**에서 사용한다. 프로세스 내부의 동시 HTTP 요청은 잠금과 기대 버전으로 직렬화하지만, 독립된 여러 백엔드 프로세스가 같은 상태 DB를 공유하는 분산 쓰기는 지원하지 않는다.

등록 인증서가 활성이고 현재 매핑이 `active`인 장치만 조회·보고할 수 있다. 사용자 발행·조회에는 기존 사이트 접근 권한을 적용한다. 장치 매핑이 바뀌면 이전 매핑에서 요청한 설정을 전달하지 않으며, 새 매핑에 새 버전을 발행해야 한다. 펌웨어도 응답의 사이트·설비·장치가 로컬 ID와 일치하는지 확인한다.

설정 이력이 있는 장치는 삭제해 같은 ID를 재사용할 수 없고 비활성화로 관리한다. 새 물리 장치에는 새 장치 ID와 전용 토큰을 사용한다. 토큰 폐기는 추가 조회·보고를 막을 뿐, 이미 적용된 설정을 원격으로 되돌리지는 않는다.

### 저장소 업그레이드와 서버 롤백

일반 상태 DB의 `runtime_state.schema_version`은 **2**다. 원격 설정 HTTP의 `schemaVersion: 1`과 펌웨어 NVS blob 형식 1은 별개이며 변경하지 않는다.

- 시작 시 기존 상태 DB v1을 단일 쓰기 트랜잭션으로 v2로 전환한다. 기존 필드는 유지하고 `deviceConfigs`가 없을 때만 빈 객체를 추가한다. 초기 PR25(`7d0678f`)가 v1로 저장한 설정도 버전·명령 ID·적용 결과·이력을 그대로 보존한다. 전환 시 revision만 한 번 증가시키고 마지막 업무 변경 시각은 유지한다.
- 손상된 JSON, 잘못된 `deviceConfigs`, 미지원 상위 스키마는 초기화하지 않고 시작을 실패시킨다. 전환이 실패하면 이전 payload·버전이 남는다. v2에서 `deviceConfigs`가 누락돼도 빈 상태로 간주하지 않는다.
- v1만 지원하는 구버전 서버는 v2 DB 읽기를 거부한다. DB 트리거도 이전 형식의 INSERT/UPDATE를 차단하므로, 전환 전에 상태를 읽은 구버전 프로세스가 나중에 저장해 설정 버전을 지울 수 없다. 같은 스키마를 사용하는 여러 프로세스의 동시 운영을 허용하는 기능은 아니다.
- 배포 전에 기존 백엔드를 중지하고 상태 DB를 일관되게 백업한다. 문제가 생기면 **v2 호환 서버로 복귀하거나 전진 수정**한다. 구버전 서버를 띄우기 위해 스키마 숫자를 낮추거나 트리거를 제거하지 않는다. 새 서버를 재배포하면 기존 설정 버전에서 계속된다.
- 장치에 적용된 버전은 서버 백업 복원만으로 되돌아가지 않는다. 오래된 DB 백업만 복원해 운영을 재개하면 장치 NVS와 충돌할 수 있으므로, 복구 시 장치의 마지막 적용 버전과 서버 이력을 함께 확인해야 한다. 이 구현은 오래된 백업에서 유실된 버전을 자동 재구성하거나 장치 NVS를 초기화하지 않는다.

### ID 호환 범위

`SITE.DOT`, `SITE.DOT-MOT.01`처럼 점을 포함한 ID도 설정 발행·장치 적용·재부팅 복원을 지원한다. 서버와 펌웨어는 위의 동일한 ID 규칙을 사용하며 설정 수신 중 ID를 잘라내거나 정규화하지 않는다.

일반 등록 API의 기존 ID 허용 범위는 바꾸지 않는다. 등록 가능한 대상이라도 원격 설정 규칙 밖의 ID(64바이트 이상, 공백, 슬래시, 비 ASCII 문자 등)가 있으면, 발행 전에 `409 DEVICE_CONFIG_UNSUPPORTED_ID`로 거부한다. 버전·pending·감사 이력을 생성하지 않는다. 같은 검사는 장치 조회·결과 보고에도 적용한다.

## API

모든 경로의 `{deviceId}`는 실제 등록된 장치 ID다. 요청은 JSON과 Bearer 인증을 사용한다.

| 메서드·경로 | 인증·권한 | 동작 |
| --- | --- | --- |
| `GET /api/devices/{deviceId}/configuration` | 사용자 `device:read` + 사이트 접근 | 버전, 최신 요청, 마지막 적용 보고, 기본값·범위 조회 |
| `PUT /api/devices/{deviceId}/configuration` | 사용자 `parameter:write`, `device:read` + 사이트 접근 | 설정 전체와 기대 버전·사유를 검증해 새 요청 발행 |
| `GET /api/devices/{deviceId}/configuration/history` | 사용자 `device:read` + 사이트 접근 | 현재 매핑 범위의 최근 요청/결과 이력 |
| `GET /api/devices/{deviceId}/configuration/pending` | 해당 장치의 전용 설정 토큰 | 장치에 전달할 최신 설정. 없으면 `desired: null` |
| `POST /api/devices/{deviceId}/configuration/result` | 해당 장치의 전용 설정 토큰 | 적용/실패/거부 보고. 정확한 명령을 확인한 후 수락 |

첫 발행 본문 예시:

```json
{
  "expectedVersion": 0,
  "settings": {
    "measurementIntervalMs": 6000,
    "replayBatchSize": 2
  },
  "reason": "제한된 네트워크에서 재전송 부하 완화"
}
```

두 설정을 모두 보내야 하며, 알 수 없는 키·숫자 문자열·실수·boolean·범위 밖 값은 거부한다. 다음 발행에는 먼저 GET으로 확인한 최신 `version`을 `expectedVersion`으로 사용한다. 버전은 1부터 2,147,483,647까지 증가한다.

장치 전달 본문은 `schemaVersion: 1`, `deviceId`, `siteId`, `assetId`, `desired`로 구성된다. `desired`에는 `version`, 서버가 발급한 32자리 소문자 hex `commandId`, `settings`만 담는다. 적용 이후에도 최신 명령을 반환해 재부팅/응답 유실을 복구할 수 있다.

결과 본문 필드는 `version`, `commandId`, `status`, `settings`, `errorCode`다.

- `applied`: 요청과 같은 전체 `settings`, `errorCode: null`.
- `failed`/`rejected`: `settings: null`, `errorCode`는 `storage_failure`, `invalid_config`, `stale_version`, `version_conflict` 중 하나.
- 200 결과 확인에는 `accepted: true`, 해당 `deviceId`, `version`, `commandId`, `status`가 포함된다. 펌웨어는 이 항목을 모두 대조한다.

## 펌웨어 저장·복원·실패 처리

- 기존 `telemetry` NVS namespace 안의 `remoteConfig` 한 값에 버전·명령 ID·대상 ID·설정·CRC를 함께 저장한다. `Preferences.putBytes()`의 성공, 길이·CRC·내용 읽기 검증을 마친 후에만 런타임 값을 교체한다.
- 같은 버전/명령/설정의 재전달은 플래시를 다시 쓰지 않는다. 더 낮은 버전이나 같은 버전의 다른 내용은 거부한다.
- 설정 저장 실패 시 현재 RAM 설정을 유지하고 실패를 보고한다. 쓰기는 됐으나 읽기 검증이 실패한 뒤 재부팅했다면, 저장된 값 전체가 유효할 때 복원하고 그 버전의 적용 결과를 다시 보고한다.
- 성공 결과의 HTTP 응답을 잃으면 다시 보고한다. 재부팅 후에도 저장된 설정으로 결과를 재생성할 수 있다. 새 요청 때문에 409가 반환되면 이전 결과 전송에 갇히지 않고 최신 요청을 다시 조회한다.
- 유효한 저장 설정은 네트워크나 설정 채널이 없어도 복원한다. 손상된 값이나 다른 대상 ID의 값은 지우지 않고 채널을 비활성화하며, 안전한 기본 대기/재전송 값으로 수집을 계속한다. 적용 성공을 보고하지 않고 로컬 점검을 요구한다. 원격 복구를 명목으로 sequence·텔레메트리 NVS 전체를 초기화하지 않는다.
- 정상 폴링은 작업 완료 후 약 30초, 결과 보고는 다음 가능한 메인 루프에서 수행한다. 통신 실패 재시도는 5초부터 최대 60초까지 늘린다. 저장 실패는 결과 보고 후 다음 정기 폴링에서 같은 명령을 재시도한다. 측정 대기·다른 처리 시간도 있으므로 즉시 적용 SLA는 아니다.
- 호출당 제한된 HTTP 작업 한 번만 수행한다. 연결/읽기 타임아웃은 각각 1.5초, TLS handshake 상한은 3초다. 서버 응답은 알려진 Content-Length 2048바이트 이하만 읽는다. 알 수 없는 chunked 응답은 적용하지 않는다.

## 검증

- `tests/test_remote_config.py`: 허용 범위·권한·장치별 인증·동시 발행·늦은 결과·재시작·저장 실패 rollback·이력·실제 HTTP 경로.
- `tests/test_runtime_store_migration.py`: 구버전 저장 코드 fixture로 v1→v2 전환, 구버전 시작/저장 거부, 재배포 시 버전 보존, 동시 초기화, 전환 실패·손상·상위 스키마를 검사한다. 설정의 실제 발행→롤백 거부→재발행은 `test_remote_config.py`에서도 검증한다.
- `firmware/esp32_edge_node/test/test_remote_config/test_main.cpp`: 적용/복원, NVS 실패/불확실한 쓰기, CRC 손상, ID/버전/숫자 형식, 결과 ACK와 재시도 간격.
- 네이티브 테스트 실행 파일을 `IOT_CONFIG_FIXTURE_EXE`에 지정하면 실제 백엔드 응답 → C++ 적용 → 재부팅 모사 → 백엔드 결과 보고를 검사한다. 공개 API 함수로 등록한 점 포함 ID, 1바이트·63바이트 경계도 같은 왕복 경로로 검사한다. PC 저장 모형이며 실제 NVS 전원 차단 시험은 아니다.
- 표준 펌웨어 테스트 명령은 `platformio test -e native -f test_remote_config`, 보드 빌드는 `platformio run -e esp32-s3-devkitc-1`이다. 네이티브 컴파일러가 없는 환경에서는 기존 로컬 Zig 도구로 같은 C++ 파일과 Unity를 빌드할 수 있다.

실제 ESP32 적용·전원 차단·TLS 운영망·장시간 통신 단절 시험은 미실행이다. 실제 배포 전에 선택한 간격이 이벤트 판단·운영 지연 요구사항에 맞는지도 확인한다.
