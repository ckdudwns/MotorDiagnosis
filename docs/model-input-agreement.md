# 실측 진동 모델 입력 합의안

- 작성일: 2026-09-08
- 상태: **초안 — 담당자 승인 전, 운영 규격 확정 아님**
- 작업 브랜치: `feat/continuous-vibration-windows` (PR35를 올렸던 브랜치)
- 범위: 모델 적용 전에 수집·특징 생성·전달·품질 계약을 맞춘다. 모델 선택, 임계값, 알림 정책을 승인하는 문서가 아니다.
- PR35는 머지 없이 닫혔으며 로컬 변경은 보존되어 있다. 이 문서가 PR 재개·커밋·배포를 의미하지 않는다.

후속 구현: [원시 XYZ 전송·서버 변환](raw-vibration-windows.md)을 로컬에 추가했다.
아래는 합의 당시 기준과 미확정 항목이며, 새 API 구현을 최종 모델/품질 허용치 승인으로 해석하지 않는다.

## 1. 이미 주어진 요구와 현재 구현 기준

| 항목 | 기준 | 상태 |
| --- | --- | --- |
| 하드웨어 | ESP32-S3 + ADXL345(SPI) + INMP441(I2S) | 사용자 확인 조건 |
| 빌드 | N8 / 8MB Flash / PSRAM에 의존하지 않음 | 현재 연속 수집 빌드 기준, 실보드 검증 필요 |
| 진동 | ADXL345 ±16g full-resolution, XYZ 모두 사용 | 사용자 확인 조건 |
| 구간 | 800Hz, 축별 512샘플, 640ms, hop 512, 중첩 없음 | 현재 구현 기준 |
| 처리 | 정상 운용 시 모든 구간을 각각 처리, 통신은 배치 가능 | 사용자 요구 |
| 목표 | 우선 정상/이상 구분, 고장 종류 구분은 후속 | 사용자 요구 |
| 음향 | INMP441 16kHz 수집 유지, 이번 진동 모델 입력에서는 제외 | 현재 분리 기준 |
| RPM | 입력에 포함하지 않으며 미측정 값을 추정값으로 채우지 않음 | 현재 후보 기준 |

SPI 핀은 CS10/MOSI11/SCK12/MISO13, I2S는 BCLK4/WS5/SD6이다. 배선 확정과 센서 부착·축 방향 검증은 별개다.

원시 입력의 논리 형태는 `[512, 3]`, 각 행은 같은 시점의 `[X, Y, Z]`, 단위는 `g`다.
현재 펌웨어는 레지스터 count에 `0.0039 g/LSB`를 적용한다. 센서 설정·교정 근거를 수집 기록에 남겨야 하며,
`vibrationRmsRaw`라는 이름만으로 이 변환과 같다고 간주하지 않는다. `g`를 mm/s 또는 음향 dB로 표시하지 않는다.

공개 학습 데이터의 12.8kHz→800Hz 필터·리샘플링은 공개 데이터 준비 전용이다. 이미 800Hz로 측정한 ADXL345 데이터에
그 변환을 다시 적용하지 않는다. 동일 샘플링 속도만으로 센서 잡음·부착·대역 특성이 학습 데이터와 같아지지 않는다.

## 2. 입력 경로 — 모델 기준으로 맞춤

사용자 방향 확인: **“모델에 맞춰”**. 장치에서 현재 보내는 특징 수에 맞춰 모델을 축소하지 않고,
최종 전달 모델의 버전별 입력 계약을 기준으로 수집·변환을 맞춘다. 현재 확인된 66개 연구 후보를 지원하기 위한
구현 방향은 아래 B(원시 XYZ → 서버 특징 계산)다. 이 방향 확인을 RF66의 최종 운영 채택이나 성능 승인으로 해석하지 않는다.

| 선택 | 장치→서버 | 모델 입력 | 현재 부족한 부분 |
| --- | --- | --- | --- |
| A: 현재 특징 경로 유지 | 구간별 기본 21개 | base21 또는 파생 ratios36/log_ratios36 | 최종 모델을 이 입력으로 제한하고 정확한 순서·수치 정책 확인 |
| B: 66개 후보 지원 | 구간별 원시 XYZ를 추가 전달·보존 | 서버에서 spectral66 생성 | 원시 수집 버퍼·버전별 API·저장·특징 추출·부하 검증 개발 |

**진행 기준: 모델이 요구하는 정보를 보존하도록 B를 우선 설계한다.** 원시 XYZ를 보존하면
동일 구간에서 특징을 다시 계산하고 센서 계산과 학습 계산을 대조할 수 있다. 대신 통신·저장 비용이 증가한다.
기본 21개만으로 추가 45개를 복원하거나, 없는 값을 0으로 채우거나, 서로 다른 구간을 합쳐 만들지 않는다.
장치에서 66개를 직접 계산·전송하는 대안도 가능하지만 현재 구현이 아니며 별도 자원·수치 일치 검증이 필요하다.

원시 int16 XYZ만 계산하면 한 구간은 `512×3×2 = 3,072 bytes`, 초당 평균 4,800 bytes,
하루 414,720,000 bytes(약 415MB/장치)다. 이는 메타데이터·JSON/base64·DB·통신 오버헤드·복제를 제외한 값이다.
기존 64개 **특징** 큐에 원시 구간을 그대로 넣을 수 있다고 가정하지 않는다. 원시 큐 용량·영속 저장·보관 기간은 B 선택 후 설계한다.

## 3. 기본 21개 계산 계약

프로필 ID: `mcc5-vibration-800hz-xyz-v1`.
이름은 아래 각 항목에 `vibrationX.`, `vibrationY.`, `vibrationZ.`를 붙인다.
순서는 **X의 7개(0~6) → Y의 7개(7~13) → Z의 7개(14~20)**다.

| 축 내 순서 | 특징 | 정의 |
| --- | --- | --- |
| 0 | rms_ac_g | 평균 제거 신호의 RMS, g |
| 1 | peak_ac_g | 평균 제거 신호 절댓값 최댓값, g |
| 2 | kurtosis_pearson | 중심 4차 모멘트 / 분산², 초과첨도 아님 |
| 3 | power_0_50_g2 | [0,50)Hz 파워 합, g², DC 제외 |
| 4 | power_50_100_g2 | [50,100)Hz 파워 합, g² |
| 5 | power_100_200_g2 | [100,200)Hz 파워 합, g² |
| 6 | power_200_350_g2 | [200,350)Hz 파워 합, g² |

모든 특징 전에 **구간별·축별 평균을 제거**한다. FFT만 평균 제거하고 RMS에 중력을 포함하는 식으로 혼용하지 않는다.
512-point FFT, periodic Hann `w[n]=0.5-0.5*cos(2πn/512)`을 사용한다.
단측 파워는 `abs(rFFT(signal*w))² / (512*sum(w²))`이며 DC는 0, 양의 내부 bin은 2배, Nyquist는 2배 하지 않는다.
주파수 간격은 1.5625Hz이며 대역은 실제 bin의 주파수로 선택한다. 상한 350Hz는 제외한다.

파생 36개는 기본 21개 뒤에 X/Y/Z 순서로 각각 네 대역 파워 비율과 crest(peak/RMS)를 붙인다.
비율 분모는 해당 축의 위 네 대역 파워 합이다. log_ratios36은 RMS/peak에 `log1p(v/0.01)`,
파워에 `log1p(v/0.0001)`를 적용한다. Pearson 첨도와 추가 비율은 같은 로그 변환을 하지 않는다.
서버 수집 단계에서 모델 학습용 평균·표준편차를 임의 적용하지 않는다. 모델별 변환은 아티팩트 계약으로 별도 명시한다.

## 4. 66개 후보의 차이 — 선택할 때만 적용

연구 프로필 ID: `mcc5-vibration-800hz-spectral66-v1`. 최종 운영 채택 여부는 미확정이다.

- 0~20: 위 기본 21개.
- 21~34 / 35~48 / 49~62: X / Y / Z 각각 추가 14개.
- 63~65: 평균 제거 XYZ의 signed Pearson 상관계수 XY, XZ, YZ. 이 계산에는 Hann을 적용하지 않는다.

축별 추가 순서는 상대 파워 8개 `[0,25), [25,50), [50,75), [75,100), [100,150), [150,200), [200,275), [275,350)`Hz,
정규화 엔트로피, 중심 주파수, 대역폭, 최대 파워 주파수, 최대 bin 파워 비율, 85% rolloff 순이다.
분모는 **0Hz 초과·350Hz 미만** bin 파워 합이다. 상세 수식은 [스펙트럼 특징 명세](mcc5-spectral-strengthening.md)를 따른다.

주의: 현재 연구 학습 입력은 기본 21개를 float32로 변환한 후 float64로 승격하고 추가 45개는 float64를 사용한다.
`extract66()` 출력에 이 정책이 전부 적용되어 있다고 가정하지 않는다. 현재 학습 경로의 `load_spectral()`은
기본 21개를 기존 캐시 값으로 교체한다. 운영 변환에서도 동일 수치 정책을 명시하고 golden으로 확인해야 한다.
기존 dense 로더에 연구용 RF/HGB joblib 파일을 그대로 넣는 것은 지원하지 않는다.

## 5. 전달·시간·품질 계약

기존 구현 API는 `POST /api/devices/{deviceId}/vibration-windows`, body는 `{"windows":[...]}`이다.
이 API는 **기본 21개 전용**이며 1~16개 배치, 최대 64KiB다. 원시 배열/66개를 이 API에 임의 추가하면 안 된다.
B 선택 시 별도 버전 계약을 정의하고 기존 21개 프로필을 조용히 변경하지 않는다.

| 필수 정보 | 합의 기준 |
| --- | --- |
| deviceId / siteId / assetId | 실제 활성 장치·설비 매핑과 일치 |
| bootId / windowIndex | 부팅별 고유 ID + 단조 증가 순번; 누락 후 재번호 부여 금지 |
| timestamp | 구간 시작 측정 UTC; 업로드 시각으로 대체 금지 |
| startUptimeUs | 같은 구간 시작의 장치 단조 시계, µs |
| sampleRateHz / sampleCount | 설정 800Hz + 실제 축별 샘플 수, 정상 구간은 512 |
| profileId / axes / unit | 버전 ID / X,Y,Z 순서 / g |
| quality / features | 품질 상태 + 21개; 불량 구간은 features=null |

재전송은 같은 ID와 같은 내용을 유지한다. 중복은 한 번만 저장하며 다른 내용으로 덮어쓰지 않는다.
수집 속도와 업로드 주기는 별개다. 전송이 늦더라도 측정은 이어지고 각 구간의 순번·시각은 유지되어야 한다.

현재 품질 상태: `valid`, `fifo_overrun`, `sensor_unavailable`, `sample_gap`, `clipped`, `constant_axis`, `processing_overflow`.
모델 미설정은 처리 상태 `waiting_model`, 불량은 `unavailable`이다. 둘 다 정상 판정이 아니다.
센서 포화·상수축·누락과 숫자 형식 오류를 구분하고 누락 수를 기록한다. 원시 카운트 레일 검사와 PC의 ±16g 검사는
경계가 완전히 같다고 가정하지 말고 경계 fixture와 품질 우선순위로 맞춘다.

행 개수×0.640만으로 수집 시간 검사 통과를 선언하지 않는다. 순번에 따른 uptime 간격과,
첫 구간부터 각 구간까지 timestamp/uptime의 누적 경과를 함께 검사한다.
로컬 수집 검사 도구에는 누적 시각 대조 수정이 있지만 PR35는 닫힌 상태이며 이 문서로 검증·배포 완료를 선언하지 않는다.
그 도구의 1초 시각 표현 허용량은 샘플링 오차 허용치나 진동·음향 동기화 정확도를 뜻하지 않는다.

| 모델별 특징 순서·정규화·입력 shape·로더 형식 | AI + 백엔드 | 후보별 확인 필요 |
| 정상 조건별 독립 운전 기록 수·분량 | 수집 담당 + AI | 미확정; 초기 5분 점검은 최종 학습 분량 아님 |

AI 담당자는 특징 추출 코드 버전/해시, 전체 순서 목록, 입력 shape/dtype, 정규화 적용 위치,
원시 XYZ 예제와 기대 특징을 제공한다. 모델 파일이 아직 없어도 여기까지 대조할 수 있다.
원시 예제에는 단위·샘플 수·축·품질을 포함하고 파일 해시를 함께 기록한다.

## 7. 모델 파일 없이 가능한 합의 검증

1. 동일 원시 구간에서 장치 C++·서버·학습 Python의 21개 특징을 승인된 오차로 비교한다.
2. B 선택 시 서버 66개와 학습 입력의 66개를 비교한다. 특징값뿐 아니라 이름·순서·수치 변환도 대조한다.
3. 상수축, 포화 경계, 샘플 누락, 비유한 값, 중복/다른 내용 재전송, 시각 정지/역행/누적 드리프트를 검사한다.
4. 정상 통신 10분 동안 약 937~938개 완성 구간과 순번·시간 일치를 확인한다. 개수만으로 통과시키지 않는다.
5. 통신 지연·재시작에서 실제 손실과 표시된 손실을 대조한다. 버퍼가 유한한 상태에서 무한 무손실을 약속하지 않는다.

모델 점수·판정 일치와 현장 성능/알림 시험은 모델 파일 도착 후 별도로 수행한다.
후속 연속 판정 연구가 있어도 기본 모델 입력을 몰래 5구간으로 바꾸지 않는다. 매 구간 점수 계산과 이벤트 지속성 정책은 별개다.
