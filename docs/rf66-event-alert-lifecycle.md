# RF66 이벤트·알림 수명주기

## 범위와 활성화

원시 구간의 RF66 비교 추론·3구간 확인은 유지하고, 별도 이벤트 정책
`rf66-event-lifecycle-v1`을 연결한다. 현장 검증 완료를 의미하지 않으며
`anomalyScore`, 기존 통계 이벤트, 모델의 단일 구간 score/verdict는 변경하지 않는다.
RF66 이벤트는 `source=rf66`, `eventType=rf66_anomaly_candidate`로 구분하며
기존 점수 필드는 null, RF66 점수는 `rf66Score`(0~1)에 저장한다.

서버 시작 시 `RF66_EVENT_MODE`로 선택한다. 잘못된 값은 시작 실패로 처리한다.

| 값 | 동작 |
| --- | --- |
| shadow (기본) | 비교 추론만. 새 RF66 이벤트·알림을 만들지 않음 |
| events | RF66 이벤트 기록·화면 조회. 수동 테스트를 포함한 RF66 알림 금지 |
| alerts | 이벤트 기록 및 기존 알림 정책에 따른 발생/복귀 알림 허용 |

설정 변경은 서비스 재시작 후 적용된다. DB 경로·계정·장치 토큰·모델 경로는
유지한다. 이 변경 자체가 운영 설정을 활성화하거나 서버를 재시작하지는 않는다.

```ini
[Service]
Environment=RF66_EVENT_MODE=events
```

실제 알림을 활성화하려면 `alerts`로 설정하고 기존 알림 정책의 사용 여부,
사이트·설비 범위, critical 심각도, 작업 시간, 채널·수신자·재전송 설정을 확인한다.
web 채널은 웹 알림 목록, webhook/email은 기존 서버 설정 어댑터를 사용한다.
이 PR은 수신자나 외부 전송 주소를 새로 설정하지 않는다.

## 발생·유지·해제

- 발생: 같은 장치·설비·부팅·프로필·모델·임계값·운영 모드의 유효한 연속
  3구간에서 모두 `score > threshold`이면 하나의 open 이벤트를 생성한다.
- 유지: 이상이 계속돼도 같은 이벤트를 유지하며 반복 발생 알림을 만들지 않는다.
- 자동 해제: 동일 설비·모델의 유효한 연속 **정상 후보 3구간**에서 모두
  `score <= threshold`이면 closed와 `endReason=three_normal_windows`를 기록한다.
  혼합 3구간(이상 미확인)은 해제 조건이 아니다. 물리적 고장 해소 확정도 아니다.
- 누락·재부팅·품질 불량·추론 실패·모드 변경은 누적을 초기화한다.
  열린 이벤트를 정상 복귀로 종료하지 않는다.
- 시작 uptime 간격은 기존 정책과 같은 640ms ±10ms로 대조한다.
- 측정 시각이 처리 시각보다 30초 넘게 오래됐거나 5초 넘게 미래이면
  이벤트 발생/해제에서 제외한다. 단일 구간 추론 결과는 그대로 보존한다.
- 30초 넘게 입력이 끊기면 열린 이벤트의 관측을 unknown으로 바꾸고 유지한다.
- 모델·설비가 바뀌면 이전 이벤트를 새 모델의 정상값으로 해제하지 않는다.
  운영자가 이전 이벤트를 검토해 명시적으로 수동 해제해야 새 이벤트를 시작할 수 있다.
  장치 부팅 변경만으로 모델·설비가 같을 때는 새 부팅의 정상 3구간으로 복귀 가능하다.

## 수동 해제

서버 내장 화면의 이벤트 상세에서 권한 있는 사용자가 사유를 입력하고 확인한다.
`POST /api/events/{eventId}/rf66-resolve`, 본문 `{"reason":"점검 및 해제 사유"}`.
`event:review` 권한 및 해당 사이트 접근 권한이 필요하며 사유는 1~500자다.
작업자·시각·사유를 원시 DB 이벤트에 보존하고 `operator_resolution`으로 종료한다.
센서 정상 복귀로 표현하지 않고 복귀 알림도 보내지 않는다. 재요청은 중복 해제하지 않는다.
일반 검수 라벨/메모 변경은 이벤트 수명주기를 종료하지 않는다.

## 영속성·중복 방지·알림

- 원시 DB의 `rf66_event_state`, `rf66_incidents`에 상태와 이벤트를 구간 결과와
  같은 트랜잭션으로 저장한다. 저장 실패 시 구간이 queued로 남고 누적도 전진하지 않는다.
- 이벤트 ID/버전으로 기존 runtime DB에 반영한다. 반영 후 확인 저장에 실패하더라도
  재시도는 같은 이벤트를 갱신하므로 중복 생성·사이트 이벤트 수 증가가 발생하지 않는다.
  검수 라벨·검수자·메모는 갱신 중 보존한다.
- 이벤트 coordinator는 자동 알림을 끈 테스트 서버에서도 이벤트 반영을 계속한다.
- 발생/복귀를 분리한 키로 기존 alert outbox에 접수한다. 채널·정책·수신자별로
  중복을 방지하고 기존 3회 한도·지수 재시도·영속 이력·수신자 범위를 유지한다.
- 실제 전송 직전에도 RF66 운영 모드, 모델, 활성 장치 매핑, 최신 입력,
  해당 발생/복귀 전이의 유효기간(30초)을 확인한다. 꺼진 모드·품질 불량·단절·
  이미 종료된 발생 알림은 전송하지 않고 실패 사유를 기록한다.
- 외부 전송은 at-least-once다. 외부 서비스 수신 후 응답 유실/프로세스 중단 시
  재시도할 수 있으므로 기존 Idempotency-Key 또는 이메일 Message-ID로 수신 측 중복 제거가 필요하다.
- 작업 시간·검수 완료·cooldown 등 기존 정책 때문에 억제된 알림은 자동 재생하지 않는다.
  과거 events 모드 이벤트를 alerts로 바꿨다고 소급 발송하지 않는다.
- 한 raw/runtime/alert DB 집합에는 서버 프로세스를 하나만 사용한다. 세 DB를
  함께 백업해야 하며 runtime/alert DB만 과거 버전으로 복원하는 절차는 지원하지 않는다.
- 이벤트 저장 한도는 10,000개다. 한도에 닿으면 새로운 사건의 원시 처리에
  backpressure를 걸며 accepted 구간을 자동 삭제하지 않는다. 기존 사건·이력은 보존한다.
  장기 보존·백업·용량 경보·보관본 정리는 운영 마무리 단계에서 별도 구성한다.

## 화면과 검증

원시 조회 API는 `eventPolicy`, 각 결과는 `eventLifecycle`을 반환한다.
서버 내장 RF66 화면은 운영 모드를 표시하고, 기존 이벤트 목록·상세·웹 알림 목록을
사용한다. RF66 이벤트 상세는 해당 RF66 특징·정책을 사용하며 다른 요약 텔레메트리를
모델 판정 근거로 붙이지 않는다. GPT Sites는 별도 소스이므로 머지 후 동기화·배포가 필요하다.

```text
python -m unittest tests.test_rf66_events tests.test_rf66_confirmation tests.test_rf66 tests.test_raw_vibration tests.test_vibration_windows
node --test tests/test_rf66_dashboard.mjs
node tests/test_ai2_dashboard.mjs
node tests/test_week4_dashboard.mjs
```

검증은 합성 원시 구간·대역 모델·가짜 전송 어댑터를 사용한다. 실제 RF 정확도·
외부 이메일/웹훅 전달·현장 장비 시험을 수행한 것으로 해석하면 안 된다.
