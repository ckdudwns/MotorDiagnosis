# 단건 모델 사건·알림 운영

## 현재 상태

새 `/api/devices/{deviceId}/periodic-snapshots` 경로에 사건 발생·유지·복귀, 웹 조회,
수동 해제와 알림 outbox 연결을 구현했다. **교체 모델은 아직 제공되지 않았으며 `app.py`는 모델을 로드하지 않는다.**
따라서 현재 기본 실행에서 자료는 `waiting_model`이고 새 모델 사건·알림은 생성되지 않는다.
테스트용 모델을 운영 기본값으로 넣거나 RF66을 재연결하지 않았다. 실제 서버 배포·외부 발송 시험은 별도다.

## 판정 정책 `single-snapshot-event-v1`

| 입력/상태 | 처리 |
| --- | --- |
| 유효한 서버 모델 이상 판정 1건 | 해당 장치·사이트·설비·모델 연결의 사건 생성 |
| 같은 연결의 후속 이상 판정 | 같은 사건 유지, 최근 근거 갱신, 반복 알림 없음 |
| 같은 연결의 유효한 정상 판정 1건 | 사건 닫기, 정상 복귀 근거 보존 |
| 불량 품질·판정 불가·새 입력 처리 대기·미수신 | 열린 사건을 `unknown`으로 표시, 정상 복귀로 취급하지 않음 |
| 모델·전처리·임계값·측정 대상 변경 | 이전 사건은 관측 불명; 새 연결의 정상값으로 이전 사건을 닫지 않음 |
| 늦은 도착·이미 더 최신 측정이 있음·60초보다 오래된 입력 | 사건 생성/복귀에 사용하지 않고 제외 사유 저장 |
| 수동 해제 | 작업자·시각·사유를 기록하고 종료; 센서 정상 복귀 및 복귀 알림으로 취급하지 않음 |

모델이 계산한 점수에 해당 모델의 `>`, `>=`, `<`, `<=`와 임계값을 그대로 적용한다.
RF66의 0.791... 임계값, 0~100 통계 점수, 연속 3구간 정책은 사용하지 않는다.
보드의 `NORMAL`/`ANOMALY_ACTIVE`, 이상 3회·정상 5회 카운터는 **장치 보고값**이지 서버 모델 판정·정답이 아니다.
서버 사건의 기본 심각도는 기존 알림 정책과 연동하는 `critical`이지만, 제목과 근거는 **모델 이상 후보**로 표시한다.
이는 실제 고장 확정·현장 정확도 검증 결과가 아니다.

### 시각·순서 기준

- 사건 전환은 처리 시각 기준 측정 나이가 **-5~60초**인 최신 측정에만 허용한다. UTC는 수신된 timestamp를 사용한다.
  5분 주기는 측정 후 전송을 5분 지연시키는 뜻이 아니라 그 시점의 구간을 선택하는 정책이므로 전환 지연 허용과 구분한다.
- 장치별 최신 여부는 **측정 시각**, 동일 시각에서는 기존 저장 우선순위로 정한다. HTTP 도착 시각으로 판단하지 않는다.
  `lateArrival` 구간은 정상/이상 어느 쪽이든 과거 이력으로 남기고 사건을 바꾸지 않는다.
- 더 최신 입력이 이미 수신되었으면 이전 판정이 먼저 끝났더라도 현재 사건 전환·알림에 사용하지 않는다.
  이벤트 처리기가 실행되기 전이라도 알림 발송 직전 최신 수신 원본을 다시 검사한다.
- 열린 사건의 관측 유효기간은 마지막 보드 보고의 정상 300초/이상 10초에 유예 60초를 더한 값이다.
  기한을 넘기면 `unknown`으로 유지한다. 단건 수신으로 장치의 온라인/오프라인 상태를 바꾸지는 않는다.
- 구간 번호는 띄엄띄엄 전송될 수 있다. 번호 차이·640ms 간격·누적 3구간을 요구하지 않는다.
  재부팅 자체를 복귀로 보지 않지만, 재부팅 후 **동일 대상·모델의 새 유효 정상 판정**은 독립적인 복귀 근거로 사용할 수 있다.
- 한 모델 연결당 장치의 열린 사건은 최대 1개다. 다른 모델 연결은 별도 사건이며 이전 모델 사건은 수동 점검·해제할 수 있다.

## 운영 모드와 알림

`create_server(..., snapshot_event_mode=...)` 또는 `app.py`의 `SNAPSHOT_EVENT_MODE`로 지정한다.
지원하지 않는 값은 기동 시 거부한다. 변경은 서버 설정·재시작으로 수행하며 웹에서 임의 변경하는 API는 없다.

| 모드 | 사건 | 알림 |
| --- | --- | --- |
| `shadow` | 생성하지 않음 | 발송하지 않음 |
| `events` **기본** | 생성·유지·복귀 기록 | 발송하지 않음 |
| `alerts` | 생성·유지·복귀 기록 | 기존 정책·채널 조건을 통과한 발생/복귀 알림 허용 |

운영 모델을 연결한 뒤 알림을 켜려면 `SNAPSHOT_EVENT_MODE=alerts`와 기존 알림 정책의 활성화·사이트/설비 범위·
심각도·운영 시간·수신자·채널 설정이 모두 필요하다. 이 변경으로 기존 정책이나 외부 수신자를 자동 수정하지 않는다.
`auto_alerts=False`는 발송 작업을 끄지만 사건 처리·조회는 계속한다.

- 사건 ID·발생/복귀 전환·정책·채널·수신자별 outbox 중복 키를 사용한다.
- 이상 유지 중에는 최근 근거만 갱신하며 새 발생 알림을 만들지 않는다. 같은 사건의 정상 복귀는 별도 전환이다.
- 과거 결과·`shadow` 자료를 나중에 `events`/`alerts`로 소급 처리하지 않는다.
  수신 당시 모드·모델 연결을 고정하며 처리 시 변경된 경우 제외한다.
  `events`에서 시작한 사건을 `alerts`로 바꾸어도 그 사건의 과거 발생/복귀를 알림으로 승격하지 않는다.
- 큐 등록과 실제 발송 직전에 모두 현재 모드, 정확한 모델 연결, 활성 장치 매핑, 최신 유효 입력,
  사건 전환 일치 및 전환 측정 시각 -5~60초를 검사한다. 수동 테스트 발송도 이 검사를 우회하지 못한다.
- 최신 입력이 불량/대기, 모델이 바뀜, 모드가 꺼짐, 전환이 오래됨/이미 복귀함 등의 경우 대기 알림도 차단한다.
  알림 억제는 안전한 미발송이며, 이후 조건이 좋아졌다고 과거 알림을 자동 복구하지 않는다.
- 전송 실패는 기존 outbox의 최대 3회 재시도와 동일 배달 ID를 사용한다.
  외부 채널은 네트워크의 불확실성 때문에 **at-least-once**이며 정확히 1회 전달을 보장하지 않는다.
  외부 수신 시스템도 배달 ID로 중복 방지해야 한다. 이미 진행 중인 외부 요청은 설정 변경으로 회수할 수 없다.
- 기존 통계 경로의 사건·알림은 유지하고 RF66 자동 사건/알림은 계속 중지한다.

## 저장·조회·수동 해제

단건 DB 스키마 3은 기존 원본·추론 결과를 보존하며 다음을 추가한다.

- `snapshot_event_jobs`: 신규 수신에만 배정하는 모드·모델 연결·처리 결과·제외 사유·사건 ID.
- `snapshot_incidents`: 사건 본문·발생/최근/복귀 근거·검수와 구분된 수동 해제·리비전·화면 투영 진행.

원본/모델 작업/사건 작업은 같은 수신 트랜잭션에서 커밋한 뒤 HTTP 202 ACK한다.
사건 처리와 추론 완료는 HTTP 응답을 지연시키지 않는 별도 작업이다.
중복 수신은 기존 200 ACK이고 사건 작업을 재배정하지 않는다.
사건 갱신과 사건 작업 완료는 하나의 트랜잭션이며 실패하면 둘 다 되돌려 재시도한다.
이후 공유 이벤트 저장소에 리비전 기반으로 반영하므로 중간 종료 후에도 사건 중복 없이 다시 반영한다.
검수 라벨·메모는 별도로 보존하고, 근거를 다른 telemetry에서 가져오지 않는다.

- **운영 현황 → 단건 진동 수신 · 새 모델 판정**: 현재 운영 모드, 모델 판정, 사건 처리 대기/완료/제외.
- **이벤트 검수**: `source: snapshot`, `SNAPSHOT-...` 사건. 발생 점수와 통계 점수 구분, 관측 상태,
  발생·최근·복귀 구간의 digest/모델/판정 조건과 수동 해제 이력.
- **운영 현황 → 웹 알림**: 발송된 단건 모델 이상 발생/정상 복귀를 구분.
- `GET /api/devices/{deviceId}/periodic-snapshots`: `eventPolicy`, 항목별 `eventProcessing`을 추가한다.
  `processed`는 해당 구간의 사건 처리 완료이지 반드시 사건 발생이라는 뜻이 아니다.
  최상위 `affectsAlerts`는 현재 모델이 있고 `alerts` 모드일 때 true다.
  개별 불변 `analysis.affectsAlerts=false`는 추론 자체가 직접 발송하지 않는다는 뜻이다.
- `POST /api/events/{id}/snapshot-resolve`, 본문 `{"reason":"해제 사유"}`:
  사용자 로그인, `event:review` 권한, 사이트 접근권한 및 1~500자 사유가 필요하다.
  작업자·사유·시각은 사건과 감사 기록에 남기며 중복 요청으로 중복 해제/알림이 발생하지 않는다.

서버 재시작·백업에 작업 및 사건 상태가 함께 포함된다. 다른 모델로 재시작하면 이전 사건을 정상으로 지우지 않는다.
저장소 전체 최대 10,000개 사건이며 자동 삭제하지 않는다. 용량에 도달하면 새 발생을 제외하고 `INCIDENT_CAPACITY`를 남긴다.
`operations inspect`에서 사건 수·대기 작업·미투영 사건을 확인할 수 있고 용량 90% 또는 미투영 시 경고한다.
스키마 3 기동 후에는 과거 코드로 DB를 직접 다운그레이드하지 않는다. 필요하면 이전 백업을 복구한다.

## 검증

```text
python -m unittest tests.test_snapshot_events tests.test_snapshot_inference tests.test_snapshot_dashboard tests.test_rf66_events tests.test_operations -q
node --test tests/test_snapshot_dashboard.mjs tests/test_rf66_dashboard.mjs
```

합성 모델과 임시 DB·메모리 채널로 사건 발생/유지/복귀, 보드 상태 분리, 중복·재전송,
늦은 정상값·수신 대기·품질 불량, 모델/매핑 변경, 알림 차단·재시도,
수동 해제·권한·검수 보존, 커밋 실패·투영 재시도·스키마 이전·백업 복원을 검증한다.
실제 하드웨어·교체 모델 정확도·외부 알림을 시험한 결과로 해석하지 않는다.
